# 账户协议抽取（QIFI 式）· 生产方案

> 借鉴 HKUDS/Vibe-Trading 的 `QIFI` 协议（"**把策略 / 账户实现解耦**"）与
> 本项目今天实测到的三处"同一规则复制多份→漂移"故障。
> **本方案是重构，会一次触及三条交易路径**，按用户要求先规划。

## 0 · 证据：三套台账的真实关系（实测对照）

| 项 | `live_ledger`（A股） | `hk_ledger` | `us_ledger` |
|---|---|---|---|
| 行数 | 268 | 109 | 108 |
| 共享函数 | `load_ledger`·`save_ledger`·`_positions`·`agent_used`·`agent_remaining`·`agent_virtual_cash`·`record_buy`·`record_sell` | ← 同 8 个 | ← 同 8 个 |
| `record_sell` 函数体 | 已扩充（含回合台账） | `69094c96` | `69094c96`（**与 HK 逐字节相同**） |
| `record_buy` 函数体 | `b3b15a0c` | `69094c96` | `69094c96` |
| `agent_used` 函数体 | `304e6090` | `32841b1c` | `32841b1c` |
| `find_holder`（分账归属查找） | ✅ | ❌ | ❌ |
| `save_deferred`（**延期单重放**） | ✅ | ❌ | ❌ |
| `roundtrip`（回合台账） | ✅ | ❌ | ❌ |
| 额度 | ¥100,000 | HK$100,000 | $10,000 |

**结论**：
1. **HK 与 US 互为副本**（函数体逐字节相同）；
2. 二者都是 **`live_ledger` 的旧版拷贝**，此后 A 股侧的改进**从未回流**；
3. 差异中**只有额度与文件路径是"有意不同"**；
   `record_buy` 的其余差异是排版 + 一处健壮性（A 股做了 `float()` 强转，HK/US 没有）。

## 1 · ⚠️ 一个应立即知道的运营缺口（不是重构的一部分）

**港股/美股没有延期单机制。** 那套是 **2026-09-01 事故复盘**后建的防线
（行情断开时减仓决策被拒且无人重试，白白浪费一个交易时段）：

| 能力 | A股 | HK | US |
|---|---|---|---|
| 被拒意图落盘 + 恢复后重放 | ✅ | ❌ | ❌ |
| 回合台账（盈亏归因的数据底座） | ✅ | ❌ | ❌ |
| 分账归属查找 `find_holder` | ✅ | ❌ | ❌ |

**HK/US 目前暂停**（`【A股优先·2026-09-04 暂停】`），所以暂无实盘影响——
**但恢复前必须补齐**，否则桥一断线，减仓意图就是静默丢失。

> 这条独立于本重构：即使不做协议抽取，也该把这三个能力补到 HK/US。

## 2 · 目标结构

```
scripts/account_protocol.py     ← 协议层：账户模型 + 纯操作（不绑市场、不绑文件、不绑额度）
    ├── 账户模型：accounts / agents / positions / deferred / roundtrips 的字段与语义
    ├── 纯操作：record_buy · record_sell · agent_used/remaining/virtual_cash
    │            · _positions · find_holder · defer/clear_deferred
    └── 回合台账：_holding_days · _roundtrip_row（今天刚加的那套，全市场共用）

scripts/live_ledger.py          ← A股实现：¥10万 + logs/ + 市场特有扩展
scripts/hk_ledger.py            ← 港股实现：HK$10万 + data/
scripts/us_ledger.py            ← 美股实现：$1万 + data/
```

**实现层的职责收窄为"绑定"**：文件路径 + 额度 + （将来）市场特有规则。
所有**算法**都在协议层，一处定义。

**为什么不是"合并成一份台账"**：三市场各自独立核算（币种、额度、分账不互通），
合并会改变账务语义。QIFI 给的正是**这个分法**——协议一份、实现按部署拆。

---

## 3 · 迁移策略（**行为保持**是第一原则）

台账是**实盘数据文件**，重构不得改变任何既有数值。

| 阶段 | 动作 | 验证 |
|---|---|---|
| **A. 建 golden 基线** | 对三套台账各录一组操作序列（买/加仓/部分卖/清仓/不存在的票），**捕获当前输出 JSON** 存为基线 | 基线即"重构前的真相" |
| **B. 抽协议层** | 把 8 个共享函数搬进 `account_protocol.py`，实现层改为薄封装 | golden 基线**逐字节**通过 |
| **C. 回补缺口** | 把 `find_holder` / deferred / roundtrip 补到 HK/US | 新增测试覆盖 |
| **D. 清理** | 删掉实现层里已上移的重复代码 | 全量测试 + golden |

**A 必须先于 B**：没有基线就分不清"重构改坏了"和"本来就这样"。

**顺序上先 A 股还是先 HK/US**：先 HK/US——它们暂停中，**改动风险为零**，
可以在低风险市场验证迁移手法，再动在跑的 A 股。

---

## 4 · 验收

1. **行为保持**：三套台账的 golden 基线**逐字节一致**（含数值精度）
2. **缺口补齐**：HK/US 具备 find_holder + deferred + roundtrip，各有测试
3. **额度/路径参数化**：改额度或路径只动实现层一行，协议层不动
4. **漂移可检测**：加一条测试断言三实现的**共享行为一致**
   （同一操作序列 → 三套产出除额度/路径外相同）——**这条是防复发的关键**
5. 实盘路径：A 股改动后，`live_hourly_analysis` 的既有测试全过

---

## 5 · 维护性（用户明确要求）

| 措施 | 理由 |
|---|---|
| 协议层无 IO、无全局状态 | 与 `test_live_ledger` 的"纯函数不碰文件"不变量一致，可直测 |
| 实现层只做绑定 | 新增市场（你说的多市场复刻）只需写一个绑定文件 |
| **一致性测试**（§4.4） | 今天三次漂移都是"没人发现两份不一样"，这条测试让它**必然被发现** |
| 迁移分 A→D 四阶段 | 每阶段独立可回退，不必一次大爆炸 |

---

## 6 · 风险与不做的事

| 项 | 处置 |
|---|---|
| **A 股台账在跑** | 放在最后动；改动前 golden 基线先立，改后逐字节比对 |
| **台账文件路径不一致**（`logs/` vs `data/`） | **本次不改**——统一路径会移动实盘数据文件，是独立决定，且与协议无关 |
| **不引入 ORM/数据库** | 保持 JSON 文件 + 纯函数，与现有一致；QIFI 的 SQL 后端对本项目是过度设计 |
| **不合并三套台账** | 见 §2 |
| **`data_asof` / 特征层** | 属 `ROUNDTRIP_FEATURES_PLAN.md`，本方案只保证台账输出可靠 |

---

## 7 · 工作量与顺序

```
① 建 golden 基线（三套）           ← 先决条件，无此不开始
② 抽 account_protocol.py           ← 核心
③ 三实现改为薄封装 + 基线比对
④ 补 HK/US 缺口（deferred/roundtrip/find_holder）
⑤ 加一致性测试（防漂移复发）
```

**建议先做 ① 与 ②**，跑通 A 股以外的一套（HK）作为样板，确认基线逐字节通过，
再推 US，**最后才动在跑的 A 股**。
