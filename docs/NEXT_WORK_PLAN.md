## P0 · 字段字典（**最该先做**）

**为什么**：不是美观问题，是**直接亏损风险**。

你的 agent 查 quantdb 看到 `total_mv = 1234`——是 1234 元还是 1234 亿元？
**差 1 亿倍**。而单位信息目前只活在**前端 TypeScript 注释**里
（`StockProfile.total_mv: number | null; // 亿元`），**agent 看不到**。

现状：字段说明是 persona 里手写的一串名字
（`dsh/baymax.trading.cordis.yml:31`），**无单位、无口径、无语义**；
库里加新字段，agent 不知道它存在。

**做法**（借用 BestAITrader 的模式，不搬它的文件）：
1. 从 **quantdb 自身**生成字段字典（`information_schema` + 列注释）→
   `configs/quantdb_fields.json`：字段名 → 中文名 / 单位 / 口径 / 示例值；
2. **让 `baymax_quantdb` MCP 工具暴露它**：agent 用字段前可查，不再靠 persona 手写；
3. **字典从库生成、不手维护**——否则又是一个会漂移的副本（今天已三次栽在这上面）。

**风险**：低。生成是离线只读；暴露是给 MCP 工具加一个查询方法，不改交易路径。

**验收**：字典覆盖 quantdb 白名单表的全部列；`total_mv` 这类量纲敏感的字段
**单位必须明确**；agent 侧能查到。

## P1 · 沙箱限价单：**结论是"先别建模"**（2026-09-13 已做第 1 步）

**做了什么**：拿历史成交量化"限价单真实成交情况"。

**查出两件事，都不是我预期的**：

1. **成交记录里没有"委托价"字段** —— `live_trade_*.jsonl` 的 `price` 与
   `fill.filled_price` **是同一个变量**（都是 `wait_fill` 拿到的真实成交价）。
   我第一版拿它俩算"滑价"，得到"16 笔全为 0.000%"——**那是同义反复**，
   不是发现。（当天第六次同源错误：**算了统计量，却没检查两个输入是否独立**。）
2. **`live_fills.py` 早就处理过这件事**：docstring 明写"账本只在真实成交后更新
   （此前按委托限价记账，成交价更优时账本少算/多算现金）"，且"**限价单通常秒成**"。

**P1 的真实结论**：
- **现在建不了撮合模型**——成交价里没有排队信息可标定
- **正确的下一步是积累**：`data/live_order_events.json` 现在只有 **1 条**未成交记录
  （`001312.SZ sell 0/300 股，限价 ¥15.5`，未成交率 1/17 ≈ 6% 但样本太小）
- 要算滑价得**先补记委托价**；要标定挂队单成交率得**先攒够未成交样本**

> 即：**先补数据，再谈建模。** 与 P0 同一套路。

## P2 · 限额口径抽取：✅ **已完成**

**做了什么**：把"限价买单口径"抽成 `live_fills.buy_limit_and_cost(price, vol, market)`
——**三市场唯一出处**，三处调用点全部改为调它。

**为什么**：这条规则此前在三个文件里各写一遍并**已实测漂移**（美/港股那份按现价算
成本，而实际下单报 `price×1.01`/`×1.005` → 单票预算与账户现金闸可被超 1%/0.5%）。

**一个必须说清的行为变化**：新实现**先对限价取整到分、再乘股数**
（`cost = vol × round(price×buffer, 2)`），旧实现是 `vol × price × buffer` 不取整。
**新版更正确**——闸门要卡的是"真实会发出去的那个限价"对应的出金。
实测最大差异 **9.60 元**（万元级单子上 0.06%）。

**测试**：`tests/test_buy_limit_cost.py`（5 个）——含"成本必须按限价、不得按现价"
这条已修 bug 的回归。

**同步发现并已修复一个"定时炸弹测试"**（2026-09-13）：

`tests/test_price_watch_run.py::test_deeper_stop_can_fire_after_shallow_order_filled`
——写于 09-12 当天通过，**过了午夜即失败**。

**根因**：`_tag_pending` 用 `now_cn()`（墙上时钟）写 `fired_ts`，而测试把
`run_watch(now=LIFE_NOW)` 冻结在 09-12、**没有冻结 `now_cn`**。于是
`_resolve_tagged` 的 `_stale_outcome` 拿「终态 ts（09-12）」与「fired_ts（真实 09-13）」
比日期 → 判成「隔日同号残留」→ 状态未知 → 不消费 → 断言失败。

**判定：测试 bug，不是产品 bug。** 生产里 `run_watch(now=None)` 会取 `now_cn()`，
两者天然一致。**已验证**：把 `now_cn` 冻结到 `LIFE_NOW` 后测试即通过。

**修法**：在 `life` 夹具层冻结 `now_cn`（`sentinel` 夹具早已这么做，本夹具此前漏了）。
即**止损逻辑本身没有问题**——它守的那个风险场景（越深的保护越先失效）生产代码处理正确。

**遗留的小味道（未改，单独排）**：`_execute_sell` 路径里有 **4 处直接调 `now_cn()`**
（`add_pending` / `_tag_pending` / `_log_line`），**不理会调用方传入的 `now`**。
把 `now` 贯穿进去能消除这个不一致（这正是让上面那个测试写成定时炸弹的原因），
但那是**动止损路径**的真重构，不宜在长会话末尾顺手做。

**为什么**：你的沙箱 `buy(signature, today_date, symbol, amount, price=None)`
**收了 price 但没往下传**，底层 `tool_trade.buy(symbol, amount)` **签名里没有价格**
——**根本没有限价单概念**。

而你的实盘有**保护价挂队**（止损报跌停价等买盘），能不能成交**取决于排队位置**。
沙箱里必然成交、实盘里可能永远等不到 —— **这条逻辑现在验证不了**。

**但先别建模型**。第 1 步是**纯离线量化**：

> 从 `live_fills` / `live_trade_*.jsonl` 的历史成交里，统计
> **限价单的委托价 vs 实际成交价、成交率、成交耗时**。

**结论会直接决定后续**：
- 若历史上限价单几乎必成交（如你的买入报 `现价×1.01`）→ **仿真价值低，不做**；
- 若挂队单（保护价）成交率明显偏低或耗时长 → 值得建模，再谈口径。

**风险**：零（只读历史流水）。

## P4 · 容器接守护启动器

**为什么**：容器现在是"**坏插件即不能启动**"，而 `restart: unless-stopped`
只会**无限崩溃重启而不自愈**。你已装 6 个插件、还会继续装。

**做法**：把已实现并实测过的 `scripts/dsh_supervised.sh` 接进容器 entrypoint
（需处理 PID 1 的信号转发）。

**风险**：中（动实盘前端容器的启动方式），但窗口可选非交易时段。
